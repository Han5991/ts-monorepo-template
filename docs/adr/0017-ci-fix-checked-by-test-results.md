# CI 자동 수정 패치는 테스트 결과로도 검사한다: 돌던 테스트는 계속 돌고, 실패한 테스트의 파일은 고치지 않는다

## 결정

- CI 자동 수정의 verify 잡이 패치를 적용하기 전과 뒤에 테스트를 돌려 테스트마다 기록을 남기고 비교한다
  (`packages/ci-fix-guard`). 아래 하나라도 걸리면 패치를 올리지 않는다.
  - 패치 전에 실제로 돌던 테스트(모드가 run·only이고, 실패를 기대하지 않고, 건너뛰지 않은 것)는 패치 뒤에도 실제로 돌아야 한다.
    지우거나 이름을 바꿔도 사라진 것으로 본다. 패치 전에 이미 돌지 않던 테스트는 보지 않는다.
  - 패치 전에 실패한 테스트 파일(테스트나 훅이 실패한 파일)과 그 스냅샷(`__snapshots__/<파일>.snap`)은 패치가 고치지 못한다.
    테스트를 실패에 맞추지 말고 테스트가 검사하는 코드를 고친다. 훅이 실패한 묶음의 테스트는 결과가 skipped로만 남고 파일 오류
    수도 0이라, 실패한 파일인지는 파일의 결과로 본다. 불러오기부터 실패한 파일은 테스트가 수집되지 않으니 여기에 들지 않는다
    (import 경로를 고칠 수 있게).
- 기록을 믿을 수 없으면 거부한다: 패치 전 기록이 없거나, 패치 전에 기록이 있던 패키지의 기록이 패치 뒤에 없거나, 실행이 중간에
  끊겼거나, 기록을 읽지 못했을 때. 비교하지 못한 채 통과시키지 않는다.
- 보고서와 비교 코드는 검사 스크립트처럼 기본 브랜치의 판을 작업 트리 밖에 복사해 쓴다. 그 자리에는 node_modules가 없으므로
  실행할 때는 Node 코어 모듈만 쓴다(lint가 막는다). verify의 테스트는 turbo가 아니라 pnpm으로 패키지마다 돌린다 — turbo는
  선언하지 않은 환경 변수(기록할 곳)를 작업에서 지운다.
- 문자열 검사(`.github/scripts/check-fix-patch.sh`)는 그대로 둔다. 빠르고 거부 이유가 분명한 첫 거름이고, 결과 비교는 그 거름이
  못 보는 꼴(별칭 import·상수 키·다른 파일에서 만든 옵션·`test.extend`)을 닫는다.
- 이 패키지의 테스트가 실제 Vitest로 보고서와 CLI를 돌린다. Vitest를 올려 보고서 API가 바뀌면 verify에서 조용히 틀리기 전에
  CI에서 먼저 실패한다.
- 못 보는 것 — 프롬프트 규칙과 리뷰가 본다:
  - 테스트가 검사하는 코드 쪽에서 테스트 입력만 특별히 다루기
  - 테스트 도우미(돌릴 대상 목록 등)나 검사 도구 코드를 느슨하게 고치기
  - 패치 전에 실패한 테스트가 읽는 다른 기대값 파일(`toMatchFileSnapshot` 대상, JSON 픽스처, `readFileSync`로 읽는 파일,
    기대값을 담은 모듈)을 실패에 맞춰 고치기 — 단언을 실패에 맞춰 바꾸는 것과 같다
  - 패치 전에 불러오기부터 실패한 테스트 파일의 테스트
  - 테스트 코드 안에서 보고서나 기록 파일을 일부러 조작하기(의도적인 코드라 리뷰에서 드러난다)

## 이유

자동 수정은 실패한 CI를 초록으로 만드는 일이라, 가장 싼 길은 테스트를 끄거나 실패한 테스트를 실패에 맞추는 것이다. 이 길을 문자열
검사로 막아 보니 리뷰를 돌 때마다 새 꼴이 나왔다(`.skip(` → `ctx.skip()` → `{ skip: true }` → `{ skip }` → `{ skip: 0 < 1 }` →
`ctx.skip.call(ctx, true)`). 문법의 꼴은 끝이 없지만 결과는 하나다 — 패치 전에 돌던 테스트가 패치 뒤에 돌지 않는다. 그래서
결과를 본다. 실패한 테스트의 파일을 막는 규칙은 프롬프트의 "단언을 실패에 맞춰 바꾸지 않는다"를 실행 경로로 옮긴 것이다.

그 테스트가 읽는 다른 기대값 파일까지는 막지 않는다. 결과만 보면 기대값을 실패에 맞춰 고친 패치와 코드를 고친 패치가 같다(실패하던
테스트가 통과한다). 테스트 파일이 기대는 파일로 보고서가 볼 수 있는 것은 그 파일이 불러온 파일(Vite 모듈 그래프)뿐이다. 거기에는
고쳐야 할 코드가 JSON 픽스처, 기대값을 담은 모듈과 같은 모양으로 든다. `readFileSync`로 읽은 파일과 `toMatchFileSnapshot`의
대상은 들지 않는다(Vitest 5.1.0에서 확인, 2026-11-21). 불러온 파일을 막으면 정당한 코드 수정까지 막힌다. 코드가 아닌 파일만
골라도 잡히는 것은 JSON import 하나뿐이다.

JSON 보고서는 쓰지 않는다. 실패를 기대하는 테스트(`it.fails`)를 보통 통과와 똑같이 `passed`로 적어, 결과를 뒤집은 패치를 가려내지
못한다(Vitest 5.1.0에서 위반을 넣어 확인, 2026-11-21). 보고서 API의 테스트 케이스는 선언된 모드(`run`·`only`·`skip`·`todo` —
다른 테스트의 `only` 때문에 건너뛴 테스트도 `skip`), 실패 기대(`fails`), 이미 뒤집힌 결과를 따로 준다.

비용: verify에서 테스트를 한 번 더 돈다(이 템플릿에서 약 5초, 테스트가 많을수록 비례한다). 실패한 테스트의 파일을 꼭 고쳐야 하는
정당한 수정(테스트가 직접 쓰는 라이브러리 API가 바뀐 경우 등)은 자동으로 고치지 못하고 사람에게 간다 — 조용히 새지 않고 멈추는
쪽이다. 테스트는 파일과 이름으로 맞춘다. 그래서 이름이 실행마다 바뀌는 테스트(`it.each`가 시간·난수 값을 이름에 넣는 경우 등)는
사라진 것으로 보이고, 그런 테스트가 있으면 정당한 수정도 사람에게 간다.
